# 分开测还是连块测？——CMDB × JOB 双系统测试策略

> 2026-08-22 定稿。回答"两个系统分开测还是连一块测"，
> 并把策略落进了代码：pytest 分层标签 + 三份新文件。

## 一句话结论

**不是二选一，是金字塔：底层分开测（占大头），顶层连块测（占小头但价值最高）。**
平台要同时支持两种模式：链路标签实现"分开"，场景矩阵实现"连块"。

## 是什么

| 模式 | 含义 | 例子 | 价值 |
|------|------|------|------|
| 分开测 | 每个系统只用自己的接口，互不依赖 | CMDB 链路：业务→主机→拓扑→模型；JOB 六链路：脚本→执行→编排→定时→账号→文件 | 故障隔离：挂了问题一定在自己 |
| 连块测 | 一个用例同时调两个系统，验证业务闭环 | CMDB 动态分组圈主机 → JOB 执行这些主机 | 验证集成缺陷：两边各自都对，放一起才暴露 |

## 为什么不能只选一个

**只分开测的盲区**：接口各自都对，但业务闭环可能断——
- JOB 的 scope_id 引用 CMDB 业务 ID，CMDB 业务被删/改 ID，JOB 全部接口静默失效
- 主机在 CMDB 转移到别的业务，JOB 侧执行范围悄悄变了
- 动态分组圈出的主机集合实时变化，JOB 执行目标跟着变

**只连块测的痛点**：
- 一个用例挂了，不知道是 CMDB 的问题、JOB 的问题还是对接契约的问题
- 必须两个系统都健康才能跑，环境重、执行慢
- 单系统细节覆盖不全（连块测天然是大颗粒场景，覆盖不了参数边界）

**一句面试话术**：分开测发现的是"功能缺陷"，连块测发现的是"集成缺陷"。
集成缺陷才是两个系统联合交付才有的问题，这正是配置平台+作业平台
联合交付的测试价值所在。

## 面试官到底在考什么（揣度）

嘉为科技是蓝鲸生态交付厂商，CMDB+JOB 是交付项目里最常见的组合。
问"分开测还是连块测"，大概率在考三点：

1. **测试分层常识**：回答"都要"太泛，回答"只分开/只连块"都露怯。
   正确姿势是金字塔：unit → 单系统链路 → 跨系统场景，比例递减。
2. **业务耦合洞察**：能不能指出两个系统的具体耦合点（数据契约），
   而不是空谈"集成"。契约四连：业务 ID、主机 ID、动态分组 ID、拓扑节点，
   都是 CMDB 生产、JOB 消费。
3. **工程落地能力**：平台怎么同时支持两种模式？答案：
   pytest 标签一键切换（`-m cmdb` 只跑 CMDB，`-m integration` 只跑连块），
   而不是写两套独立的测试工程。

## 怎么办（已落地的三层金字塔）

```
        ┌─────────────────────────┐
        │  L3 连块测 integration   │  8 用例：契约一致性/业务联动/隔离反向
        ├──────────┬──────────────┤
        │ L2 分开测 │ L2 分开测     │  CMDB 链路 5 用例（cmdb 标签）
        │  JOB 六链路 │  CMDB 链路   │  JOB 六链路 50+ 用例
        ├──────────┴──────────────┤
        │  L1 unit（纯函数/拼参自洽） │  18 用例：凭证没到也能跑，全绿
        └─────────────────────────┘
```

- **L1 unit**：不依赖环境，等邮箱期间跑，全绿（42 个）
- **L2 分开测**：`-m cmdb` 只跑 CMDB，`-m script` 只跑脚本链路——
  定位问题时先分清"病在哪个系统"
- **L3 连块测**：`-m integration`，场景矩阵按数据契约组织

**开源对齐**（2026-08-23 补充，面试可引用）：三层术语对齐
HttpRunner 的"API 层 → 用例层 → 场景层"分层思想（L1 API 层 = 客户端
封装自洽，L2 用例层 = 单系统链路，L3 场景层 = 跨系统矩阵）；平台形态
借鉴 MeterSphere：测试计划（marker 组合下拉框）、Postman 式接口调试
（只读白名单）、通过率趋势仪表盘。

## 连块测场景矩阵（端到端这一环，数据契约是抓手）

| 场景 | 用例 | 验证点 |
|------|------|--------|
| A 契约一致性 | JOB 业务 ID 在 CMDB 业务列表里 | 根契约：scope_id == bk_biz_id |
| A 契约一致性 | JOB 目标主机在 CMDB 主机列表里 | 主机契约：host_id == bk_host_id |
| A 契约一致性 | 动态分组圈出的主机合法 | 分组契约：圈人不圈空、不圈幽灵 |
| B 业务联动 | CMDB 圈主机 → JOB 执行成功 | 闭环：先查圈了谁，再执行谁 |
| B 业务联动 | 引用动态分组 ID 直接执行 | 分组直引：JOB 不关心主机清单 |
| B 业务联动 | 分组执行完成且日志正确 | 端到端全链路（含状态轮询） |
| C 隔离反向 | CMDB 不存在的主机 JOB 拒绝执行 | 安全边界：跨业务执行必须被拦 |
| C 隔离反向 | 不存在的分组 ID JOB 拒绝执行 | 契约边界：坏 ID 必须显式报错 |

## 今日落地清单

- `cmdb_client.py`：CMDB ESB 客户端（cc 组件），复用 ESB 三件套；
  与 JOB 客户端的异同写进 docstring（面试常问）
- `test_cmdb_core.py`：分开测 CMDB 半边（3 unit + 9 环境层，含写操作骨架）
- `test_integration.py`：连块测场景矩阵（9 用例，含拓扑节点契约，取代旧 e2e 文件）
