# 98 个用例全景图（分类 + 设计逻辑）

> 用途：面试 / 讲解时，用"一张图 + 一句话"讲清 98 个用例怎么分类、为什么这样设计。
> 配套《2026-08-23-用例清单.csv》看每一个用例的名字、作用、设计原因。

## 一、总账

- **98 个用例** = 90 个测试函数（其中 8 个是参数化展开的）
- = **35 个现在能跑**（unit，不碰蓝鲸）+ **63 个等账号**（环境层，蓝鲸体验环境 9 月开放）

## 二、分类关系图

```
98 个用例
│
├─ 【L1 工具层】35 个 —— 测"自己写的工具"对不对  ✅ 现在能跑
│     打包/拆包(Base64)、拼参数、分页、客户端构造、存储、Web层自身
│     特点：不碰蓝鲸，所以不等账号
│
├─ 【L2 用例层】49 个 —— 分开测两系统"各自好不好"  ⏳ 等账号
│    ├─ JOB 六链路（41 个）
│    │    ├─ 脚本管理 6
│    │    ├─ 快速执行 6  ← 最核心
│    │    ├─ 作业编排 6
│    │    ├─ 定时任务 6
│    │    ├─ 账号 + 高危 7
│    │    └─ 文件 + SQL 10
│    └─ CMDB 链路（8 个）
│         └─ 业务 → 主机 → 拓扑 → 模型 → 分组
│
├─ 【L3 场景层】8 个 —— 连块测两系统"连起来对不对"  ⏳ 等账号（核心卖点）
│     数据契约：CMDB 圈人 → JOB 干活，三个 ID 对不对得上
│
└─ 【专项横切】
     ├─ 边界（12 个）—— 参数临界值（超时 0 / 86401 该被拒）
     └─ 安全（7 个）—— 鉴权 / 越权 / 注入 / 高危命令
```

## 三、每一层"为什么这样设计"

| 层 | 为什么设计它 | 大白话 |
|---|---|---|
| L1 工具层 | 先保证"手"没坏，再谈摸系统 | 螺丝刀没拧紧，怎么拧别人 |
| L2 用例层 | 两个系统各自单独测，好定位问题 | 分开查，出问题知道是谁的锅 |
| L3 场景层 | 单独都好，连起来可能坏（ID 对不上） | 两个零件都好，拼一起可能卡 |
| 边界 | 参数有范围，越界该拦不拦会崩 | 传个 0 超时，机器卡死 |
| 安全 | 危险动作要拦，越权要隔离 | `rm -rf` 拦不住 = 删光服务器 |

## 四、面试一句话串起来

> "我 98 个用例分四层：**L1 测自己写的工具（35 个，现在能跑）→ L2 分开测 JOB 六链路和 CMDB（49 个）→ L3 连块测数据契约（8 个）→ 再横切边界和安全**。
> 每一层都对应一个真实风险：工具坏了、单系统坏了、连起来对不上、参数越界、危险命令。"
